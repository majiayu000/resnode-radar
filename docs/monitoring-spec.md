# Real VPS Monitoring System Spec

## Objective

Build a real, source-backed VPS monitoring site. The public page must display only data produced by the monitor runtime from live provider pages or explicit monitor errors. It must not ship mocked stock, price, route, or status data.

## Current Evidence

| Area | Evidence | Implication |
| --- | --- | --- |
| Entrypoints | `index.html`, `app.js`, `styles.css` static GitHub Pages site | The public UI must stay static and read generated JSON. |
| Core models | Prior `app.js` embedded handwritten products | Replace with `data/products.json` generated by monitor. |
| Runtime/lifecycle | Static GitHub Pages UI; monitor can run from local CLI, backend worker, or GitHub Actions | Keep one monitor command and make scheduler replaceable. |
| Adapters/backends | Live provider pages: VIRCS Inertia JSON, LisaHost WHMCS HTML, Lagom/WHMCS product lists, ZLIDC product-wrap HTML, AaITR Cloudflare challenge plus Reader snapshot | Implement provider adapters with explicit blocked/error states and attempt evidence. |
| Generated/config artifacts | New `monitor/sources.json` and generated `data/products.json` | Config is source list; JSON is runtime projection. |
| Errors/diagnostics | Current UI claimed monitoring without real fetch | Errors must be visible in generated data and UI. |
| Tests/headless | `npm run check` only | Add `monitor:validate` and run monitor in CI/schedule. |
| Open issues/PRs | None | Implement directly in this repo. |

## Chosen Architecture

```text
product/app
  - index.html, app.js, styles.css
  - reads data/products.json only; no embedded product fallback

core/domain
  - monitor record schema inside scripts/monitor.mjs
  - status enum: available, unavailable, unknown, blocked, error

runtime/application
  - scripts/monitor.mjs
  - fetches sources, parses provider responses, writes data/products.json

adapters/backends
  - vircs_inertia_product parser
  - whmcs_group parser
  - lagom_product_list parser for WHMCS/Lagom `.product` and `.package` cards
  - zlidc_product_wrap parser
  - aaitr_store parser with direct HTTP, WHMCS fallback URL, discovery URL, optional headless Chrome probe, and Reader snapshot fallback

plugins/components
  - optional notification hook is future work

testing/headless
  - node --check
  - scripts/validate-monitor-data.mjs
  - one live monitor run before publishing changes
```

## AaITR Adapter Contract

AaITR uses WHMCS storefront paths but currently returns Cloudflare challenge pages to this monitor runtime. The adapter must try real routes and record why product data is unavailable instead of inventing stock.

Attempt order:

1. Direct HTTP on `https://www.aaitr.com/store/srv`.
2. Direct HTTP on configured fallbacks: language variants and common `cart.php?gid=` paths.
3. Discovery fetches for `sitemap.xml` and `robots.txt`; discovered AaITR store/cart URLs are tried if present.
4. Optional headless Chrome `--dump-dom` probe for the first configured product URLs.
5. Third-party Reader snapshot for configured public AaITR pages when official direct fetch remains blocked.

If any attempt returns parseable WHMCS product DOM, parse:

- product name from WHMCS product title/header
- price from `¥...CNY` or `...元`
- stock state from `Sold Out`, `Plenty in Stock`, `库存充足`, `售罄`, `缺货`, and order button presence
- order URL from `cart.php?a=add`
- configuration fields from `key: value` lines

If direct/chrome attempts only return challenge pages but Reader snapshot succeeds, output AaITR product rows with evidence `reader_snapshot` and labels such as `快照: 库存充足`. Reader snapshot data is not treated as first-party official API data and must not claim precise price or order-link data unless the snapshot contains those fields.

If every attempt fails, output one `blocked` record with `raw.attempts`. Search engine snippets can help discover candidate URLs, but must not be used as stock truth.

## Evidence And Risk Contract

Every monitor record must include:

- `evidenceLevel`: one structured badge describing the strongest evidence behind the row, such as precise stock, official order entry, third-party snapshot, direct fetch blocked, unavailable, or fetch error.
- `riskTags`: one or more structured tags explaining buyer-facing caveats, such as only proving an order path, unstated stock, third-party snapshot, direct fetch blocked, incomplete fields, NAT/shared access, identity requirement, refund limits, or support confirmation.

These labels are evidence and risk signals, not purchase advice.

## Non-Goals

- Do not bypass Cloudflare, CAPTCHA, login, or payment walls.
- Do not claim stock when the official page only proves an order button exists.
- Do not scrape the reference site as a data source.
- Do not require a custom server for the first version.

## Readiness Language

- "Monitoring implemented" means `data/products.json` was generated from live fetches and the UI displays that JSON.
- "Blocked" means the monitor reached a provider page but could not access product data because the provider returned an anti-bot/challenge page.
- "Available" means the parser found a provider-backed positive stock count or an official order path. If stock count is not stated, the status label and evidence say it is an order entry, not a precise stock claim.
